1 · Topology at a glance

Two machines share one federated zone (sharedzone) over a raft cluster. Each runs a single nexusd-cluster daemon that hosts the kernel, the raft transport, and two plugins: a LocalConnector (backing store) and a FUSE mount (the surface Claude Code reads/writes). Claude Code's task list is routed to a per-machine path that is the FUSE mount — so every task read/write flows through the kernel.

The merged view is symmetric: each node mounts its LocalConnector into sharedzone at the same VFS path, so ls on either FUSE mount returns the union of both machines' tasks.

2 · The layer stack on each node

A single daemon, three tiers. The kernel exposes a stable syscall surface; plugins are C-ABI cdylibs that adapt an OS-level interface to those syscalls. The whole point of §3g is that the FUSE plugin is the sole I/O path for cc-tasks — so its adapter must faithfully map every file op onto the kernel.

Design rule — Adapters map OS ops → syscalls; they never change the kernel ABI. Every fix this cycle lived in a plugin adapter or a kernel idempotency check — the syscall surface stayed frozen.

3 · §3f → §3g: read ⊥ cache ⊥ materialize

The old §3f model made cross-node reads work by materializing peer bytes onto local disk (a hot-path cache-back after every fetch) and having Claude Code read that raw dir directly. That conflated three orthogonal concerns. §3g decouples them: Claude Code reads through the FUSE mount, and peer content is fetched on demand, never cached back.

✓ read ⊥ cache ⊥ materialize. Merged view = raft-replicated rows + per-read fetch. Nothing shadow-copied.

Why it's correct — cc-tasks is append-only with raft-replicated metadata rows, so no failover content cache is needed. A real read-through cache, if ever required, belongs in a dedicated CacheStore, not inlined on the read hot path.

4 · Cross-node READ flow

When one node reads a task owned by the other, the kernel routes by last_writer_address to the owner's co-located ReadBlob RPC and streams the bytes back — no local materialization.

sequenceDiagram
    autonumber
    participant U as OS (cat)
    participant F as FUSE plugin
    participant K as Kernel (sys_read)
    participant M as ZoneMetaStore
    participant B as Local backend
    participant P as Peer ReadBlob (owner)
    U->>F: read(/…/peer-task.json)
    F->>K: sys_read(path)
    K->>M: get(path)  ·  row: last_writer = PEER
    K->>B: read_content(path)
    B-->>K: MISS (not local)
    K->>P: try_remote_fetch(origin=peer, key)
    P-->>K: bytes (current content)
    K-->>F: bytes  (NOT cached back)
    F-->>U: content ✓
    Note over K,B: no write_content — read ⊥ materialize
Hard invariant — on-demand read requires last_writer_address to point at a node that actually holds the content. A row claiming last_writer=self with no local bytes is an orphan — unreadable under §3g (§3f hid this by materializing). Orphans are a cutover artifact, not a steady-state occurrence for append-only + FUSE-mediated cc-tasks.

5 · WRITE / UPDATE flow

A write (create or overwrite) commits to the local backend and proposes a metastore row stamped last_writer=self; raft replicates the row so the peer sees the entry and fetches fresh bytes on its next read. Overwrite (Claude Code's TaskUpdate) was the subtle one: WinFsp routes open(path,"w") on an existing file to a distinct overwrite disposition, and NFS to setattr(size=0) — both had to be wired to the kernel's whole-file rewrite.

sequenceDiagram
    autonumber
    participant U as OS (open "w")
    participant F as FUSE plugin
    participant K as Kernel
    participant B as Local backend
    participant R as Raft (sharedzone)
    U->>F: create OR overwrite(existing)
    alt existing file (TaskUpdate)
        F->>K: sys_write(path, &[])  ·  truncate
    end
    U->>F: write(new content)
    F->>K: sys_write(path, content)
    K->>B: write_content (whole-file)
    K->>R: metastore.put(row: last_writer=self, new content_id/size)
    R-->>K: committed (replicated)
    K-->>F: ok
    Note over R: peer now sees the row → reads v2 on demand
The overwrite fix — the frontend adapters lacked the truncate-overwrite disposition, so TaskUpdate failed under §3g (§3f wrote the raw dir natively, never through FUSE). Fixed identically on both platforms: truncate = empty whole-file write — kernel untouched.

6 · Raft membership & the DT_MOUNT deadlock fix

A 2-voter cluster needs majority = 2 for any write. Restarting both nodes at once used to deadlock: each daemon fail-loud'd installing its --mount-driver because that unconditionally proposed the DT_MOUNT row (a raft write needing a leader) — and neither had a leader yet. The fix is a raft-contract idempotency: on resume the row is already committed, so read it with a leader-free local read and skip the propose.

stateDiagram-v2
    [*] --> Booting
    Booting --> ReplayLog: read persisted raft log (leader-free)
    ReplayLog --> RowExists: DT_MOUNT already committed?
    RowExists --> WireLocal: YES → skip propose, wire backend
    RowExists --> Propose: NO (genuinely new) → propose (needs leader)
    WireLocal --> Serving: daemon stays up ✓
    Propose --> Serving: leader present (founder bootstrap)
    Propose --> FailLoud: no leader (transient)
    Serving --> QuorumForms: peer connects → elect leader
    note right of RowExists
      get-before-put:
      never re-propose committed state
    end note
    note right of FailLoud
      old bug: both nodes here
      at once → mutual deadlock
    end note
Raft contract — never re-propose already-committed state; use leader-free reads for existing state. N=2 has no fault tolerance (both must be up) — an odd N≥3 with a witness removes the “both required” cliff.

7 · The one-time §3f→§3g cutover

Flipping the live CC task dir into a FUSE mount is hard to reverse, so the launcher performs a single, safe migration: move (never delete) existing task files into the LocalConnector backend, then mount over the emptied leaf. Guarded by NEXUS_3G_CUTOVER so an incidental restart can't fire it.

8 · Invariants & hard-won lessons

Invariant / lessonWhy it matters
read ⊥ cache ⊥ materializeThe read hot path returns peer bytes; it does not write them back. Caching, if needed, is a separate concern (CacheStore).
last_writer must hold the contentOn-demand read routes by owner; a row whose owner lacks the bytes is an unreadable orphan.
Never re-propose committed stateIdempotent DT_MOUNT install; leader-free reads on resume — the raft-contract fix for the 2-voter cold-start deadlock.
FUSE is the sole I/O path (§3g)So the frontend adapter's file-op contract must be complete on every platform — and CI-guarded by a real CRUD E2E.
Docker-green ≠ live-greenThe on-demand read and both overwrite gaps were invisible to Docker (libfuse3) and only surfaced on live WinFsp / FUSE-T. Live cross-machine verification is the real gate.
Kernel ABI stays frozenEvery fix was a plugin adapter or a kernel idempotency check — the syscall surface was never touched.
Live-verified — cross-node read (bidirectional), cross-machine update propagation (Win overwrite → raft row → Mac on-demand fetch → new content, no materialization), 2-node cold-start recovery, and full CRUD through both FUSE frontends.
