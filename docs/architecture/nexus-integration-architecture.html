Constraints

  • One nexus per host. A host runs one nexusd-cluster process (the cluster profile + the managed_agent control plane, both built in nexus-vfs); its embedded kernel::Kernel is that host's nexus. That stock binary already hosts agents as ACP subprocesses. Whether it also hosts in-process sudocode agents is a build-time choice — the cohost-sudocode build (rust/nexusd) compiles the SpawnTask adapter in, the only spot that links sudocode. The nexus-bootstrap launcher protocol owns discover-or-launch, so there is one kernel per host (§8).
  • Pure-infra nexus. The kernel and the service-tier crates (services, raft, lib, contracts) compile with zero knowledge of any agent runtime — they know only the SpawnTask DI trait. The single nexus → sudocode edge is the binary edge nexusd-cluster (rust/nexusd), where both source trees link and SpawnTask<Kernel> monomorphises (§2.3). Because that edge is a binary leaf (nothing imports a [[bin]]) and sudocode_runtime only depends downward on kernel, there is no dependency cycle.
  • State SSOT. Agent runtime state (pid → AgentState, condvar wakeup, signal semantics, parent/child links, transition validation) lives in kernel::core::agents::registry::AgentRegistry. In-process Rust callers reach it directly; external callers reach it through the gRPC surface.
  • gRPC is the external surface. External clients (sudowork UI, orchestrator) reach the kernel over the VFS gRPC port; the agent↔kernel hot path stays in-process Rust.
  • Cluster profile. nexusd-cluster runs Nexus's cluster profile — bricks: IPC, FEDERATION — whether or not the sudocode agent adapter is compiled in.
  • Zone = VFS path mount point. A zone's visibility boundary is its mount path. ReBAC governs sub-path access within a zone.

2. Agent Identity & Runtime

Three namespaces along the same Linux distinction between what lives on disk and a running process — the agent profile and its sessions are persistent, the process is ephemeral:

NamespaceLifetimeContentBacking store
/agents/{name}/PersistentProfile: config.toml, prompts/, skills/, memory/, sessions/ (DT_LINK index into /sessions/)Metastore (DT_FILE / DT_DIR)
/sessions/{session-id}/PersistentTranscript SSOT (jsonl) + owner attribute + repo DT_LINKs — flat, session-id the only structural keyMetastore (DT_FILE / DT_LINK)
/proc/{pid}/EphemeralRuntime presence: status, agent link, chat-with-me, workspace/In-memory + WAL while pid alive

/agents/{name}/ is the stable identity an outsider addresses (other agents, humans on Element). One agent name can spawn many pids — different worktrees, parallel work — and all of them share the same profile.

2.1 Agent-name & session namespaces

/agents/scode-standard/          ← profile + history (DT_DIR)
   config.toml                   ← model selection, MCP endpoints, default workspace recipe
   prompts/                      ← system-prompt overrides, per-skill prompts
   skills/                       ← loadable tool sets
   memory/                       ← long-lived agent memory
   sessions/                     ← per-agent DT_LINK index (DT_DIR) — not the SSOT
      <session-id>            ← DT_LINK → /sessions/<session-id>/
/sessions/<session-id>/           ← session zone (DT_DIR) — flat, session-id is the only structural key
   transcript.jsonl              ← the conversation transcript (DT_FILE) — byte SSOT
   owner                         ← owning agent-name (attribute) — drives default visibility policy
   repos/<alias>                  ← DT_LINK → /repos/<repo>   (0..N; the repos this session touched)

/agents/{name}/ is the persistent SSOT for an agent's profile — config, prompts, skills, memory. Session transcripts are not nested under the agent: each lives flat at /sessions/<session-id>/, where the session-id (a durable UUID, not the pid — §2.3) is the only structural key. Isolation is therefore a policy, not a path. /agents/{name}/sessions/ holds DT_LINKs into /sessions/ as a per-agent enumeration index (a list(prefix) readdir, since the metastore has no by-attribute index), and an owner attribute on each session records the owning agent and drives default visibility. Cross-agent search is never structurally foreclosed — a pid may scan /sessions/ or be granted a DT_LINK into its own index, subject to policy; because a DT_LINK follow re-authorizes against the target's own permission gate (the same auth every read passes), a link is not a capability and visibility stays policy-controlled. A worker boots by reading its profile from /agents/{name}/ and the requested --session-id transcript from /sessions/<session-id>/, works, and exits; resuming re-reads the same session-id (durable, spanning many pids).

2.2 Runtime namespace

/proc/{pid}/
   status                        ← virtual file: AgentStatusResolver renders descriptor JSON
   agent                         ← DT_LINK → /agents/{name}/   (Linux /proc/{pid}/exe analogue)
   chat-with-me                  ← DT_STREAM: this pid's conversation
   workspace/                    ← DT_DIR (agent cwd)

The whole /proc/{pid}/ subtree is stamped at start_session and reaped when the task exits. /proc/{pid}/status is served by AgentStatusResolver, a PathResolver that renders the live AgentDescriptor as JSON each read.

A managed agent runs as one in-process agent loop inside nexusd-cluster, reaching the kernel through direct Rust syscalls (kernel.sys_read, sys_write, sys_watch) and the dispatch hooks through the same in-process channel every kernel observer uses. External ACP agents (claude / codex / codebuddy / nanobot) run as subprocesses over stdio, because JSON-RPC over stdio is the only protocol those binaries speak; that path lives in AcpService (§1).

Three identity layers, durable vs ephemeral: agent-name (durable principal), session-id (durable UUID — the transcript key you --resume, spanning many pids), and pid (ephemeral — one boot/run of a worker, the AgentRegistry handle). session-id ≠ pid: a session outlives any single process, so the two cannot be the same value. On start_session, ManagedAgentService mints a new session-id (or echoes the resumed one), registers a pid, plants the per-pid AgentDescriptor — the spawn-time SSOT (agent_id → desc.name, model → desc.labels["model"], workspace list → desc.repos) — stamps the /proc/{pid}/ entries (§2.2), and returns {session_id, pid, workspace_path} to the caller.

ManagedAgentService hands off to the runtime through the SpawnTask<K: KernelSyscall> DI seam — one indirect call per session start. The binary edge is nexusd-cluster (rust/nexusd, nexus repo): it constructs a concrete SpawnTask<Kernel> adapter wrapping sudocode_runtime::spawn_task and registers it via install_managed_agent_with_spawn(kernel, adapter). start_session calls provider.spawn(kernel, desc, observer) through Arc<dyn SpawnTask<K>>: exactly one vtable dispatch per session, and the returned Box<dyn SpawnHandle> lands in the service's spawn_handles sidecar. Inside the spawn body the surface is plain monomorphic Rust: spawn_task::<Kernel> and its inner run_loop are generic over K: KernelSyscall, specialised against the concrete Kernel at the binary edge, so every sys_read / sys_write / sys_watch in the mailbox loop is an inline direct call. The services rlib depends on the SpawnTask trait only; pure-Rust slim builds call install_managed_agent (no spawn provider, no per-pid task).

The production nexusd-cluster is built in nexus-vfs (rust/profiles/cluster): its run() composes the cluster boot with a2a + the managed_agent control plane — both kernel-tier nexus-vfs crates — so a minted agent's spawn/get/cancel + the raw ACP-subprocess tunnel work on the stock binary, with no sudocode linked. rust/nexusd (nexus repo) is the co-host build: the same composition plus the one nexus → sudocode edge — a concrete SpawnTask<Kernel> adapter (SudoCodeSpawnAdapter) that pulls sudocode_runtime as a library and monomorphises the spawn body in-process, wired via install_managed_agent_with_spawn under the cohost-sudocode feature. That link lives at this binary leaf because sudocode_runtime → kernel; hosting it in nexus-vfs would form a cycle. So there is no dependency cycle: nexusd → {sudocode_runtime, managed-agent, nexus-cluster}; the reusable crates stay agent-runtime-free (they know only the SpawnTask DI trait, never sudocode). The co-host build requires nexus and sudocode to resolve to one nexus-vfs kernel rev, else SpawnTask<Kernel> is two distinct types. scode stays a standalone CLI.

A worker boots by reading its profile from /agents/{name}/ and the requested --session-id transcript from /sessions/<session-id>/ (§2.1), works (appending to the transcript and the mailbox), and exits; the /proc/{pid}/ subtree is reaped. Resuming re-reads the same session-id under a fresh pid — persistent state lives in /agents/{name}/ and /sessions/, not in a long-running process. Out-of-band termination (SIGTERM / SIGKILL / orphan reap) flows through AgentRegistry::on_terminate, which reaps /proc/{pid}/ and aborts the worker via its SpawnHandle; cancel(pid) calls AgentRegistry::kill(pid, 0) for the same outcome.

After spawn, prompts and responses flow over the chat-with-me VFS surface — the same A2A primitive every agent uses (§3). sudowork writes prompts to /proc/{pid}/chat-with-me; the worker sys_watches it and writes responses to /agents/{user}/chat-with-me, which sudowork's UI watches in turn.

ManagedAgentService surface (over NexusVFSService.Call):

  • start_session_v1 — {agent_id, repos, model, owner_id, zone_id, session_id?} → {session_id, pid, workspace_path}. agent_id names the profile (/agents/{agent_id}/); the optional input session_id resumes an existing durable session (a fresh call mints a new one); pid is the ephemeral runtime handle.
  • cancel_v1 — {pid, mode} → {cancelled}; mode ∈ {turn, session} (turn aborts the current generation, session reaps the pid). Addressed by the runtime pid, not the durable session-id.
  • get_session_v1 — {pid} → {session_id, pid, agent_id, workspace_path, model, state}. Queries a live run by pid; state is the runtime FSM state, session_id the durable transcript it is attached to.

Prompt / event flow reuses sys_write / sys_watch / sys_read over the chat-with-me paths; the A2A surface carries it without a bespoke SendPrompt or SubscribeEvents gRPC.

AgentState FSM: REGISTERED → WARMING_UP → READY ↔ BUSY → SUSPENDED → TERMINATED. AgentRegistry is the SSOT: update_state(&pid, new_state) (kernel/src/core/agents/registry.rs) is the only runtime-path writer — it enforces the FSM via can_transition_to, updates updated_at_ms, and fires on_terminate on TERMINATED. The writer is a state-observer closure that ManagedAgentService::start_session constructs (capturing Arc<AgentRegistry> + pid, mapping the runtime's AgentLoopState onto AgentState) and passes through the SpawnTask::spawn seam; the adapter forwards it to the runtime's state_callback and never touches AgentRegistry. kernel.agent_wait(pid, target_state, timeout_ms) parks on the per-pid condvar for event-driven waits.

3. A2A Communication

A2A, H2A, and A2H share one primitive: write a message to the recipient's chat-with-me.

3.1 Mailbox

/agents/{name}/chat-with-me and /proc/{pid}/chat-with-me are append-only message streams. They are normal DT_STREAMs that any caller can write to and the owner can read with sys_watch. Federation Raft replicates them across zone members; reach to clients outside the federation goes through the Matrix C-S adapter (§4).

3.2 The chat-with-me link inside a workspace

/proc/{pid}/workspace/chat-with-me  →  /proc/{pid}/chat-with-me

An agent inside another's workspace writes to chat-with-me relative to wherever it stands; resolution follows back to the workspace owner's stream. The link is a plain DT_LINK row in the metastore, stamped at start_session.

3.3 Sender identity

Every write to a chat-with-me mailbox carries an unforgeable sender identity. The kernel rewrites the message envelope's structured from field to the caller's authenticated agent_id before the write reaches the backend, so a sender's from is always its own identity. Identity itself is established by the auth layer — an agent's identity certificate resolves to the agent_id (see nexus-auth-architecture); the stamp binds that identity onto the message. A mailbox write with no authenticated agent_id is rejected, so the guarantee is fail-closed.

The rewrite happens at the origin write, before Raft replication (§4). Every replica and every reader then sees the same stamped from without re-verifying, so a message's origin travels intact to another machine: agent A on one node writes from:A locally, the bytes replicate, and a reader on another node reads from:A as authored.

Cross-machine, from:A is unambiguous because agent names are unique across the cluster — but the mechanism is two-part, since the credential store is per-node (it lives in the root zone, which is per-node SOLO, never federated; each node mints and validates its own agents). Within a node, minting refuses a second credential for an existing (subject_type, subject_id) unless --allow-existing is passed (rotation). Across nodes, uniqueness is a naming convention: agent names are machine-anchored (a per-node identifier plus the agent's workspace), so two nodes cannot mint the same name. Either way an agent keeps one identity across every zone it belongs to (one actor, not one-per-zone — a node can be in many zones). See nexus-auth-architecture §4.1.

An agent authenticates with a CA-signed identity certificate and connects to its node over the required-mTLS bind (--bind-addr) — the same surface the peer plane uses. The certificate's subject type distinguishes an agent identity from a node identity, so one bind serves both. The certificate resolves to the agent's agent_id, the stamp binds that identity onto the write, and Raft carries the stamped from. See nexus-auth-architecture §4.1.

The rewrite is a registered NativeInterceptHook (MailboxStampingHook) that delegates the envelope policy to mailbox_stamping_policy::maybe_stamp_chat_envelope. Both live in the kernel-tier a2a crate (nexus-vfs/rust/a2a/) and are armed once at daemon boot via install_a2a_stamp_hook. Placing the from guarantee at the substrate makes it universal: every writer to a */chat-with-me mailbox is stamped through the same point — managed agents, external clients, and Matrix humans alike — because identity must be enforced where every write converges, not per frontend. The hook struct owns "how to be a hook" (dispatch wiring + content-clone bypass); the policy module owns "what to rewrite" (envelope schema, identity guarantee). The hook trait supports content rewriting — on_pre returns Result<HookOutcome, String>, where HookOutcome::Replace(bytes) substitutes write content; accept/reject hooks (audit, permission, workspace boundary) return HookOutcome::Pass.

To keep the hot path allocation-free for the writes that don't need rewriting, hooks declare a mutating_path_suffix and the dispatcher uses it as a double bypass:

  • Layer 1 (no mutating hooks registered): empty-Vec check, dispatcher goes straight to WriteHookCtx::content = vec![] — identical to the pre-widening cost.
  • Layer 2 (mutating hook registered, write path doesn't match): suffix scan returns false, dispatcher still passes vec![]. Only writes whose path ends in a registered suffix (*/chat-with-me) pay the content clone.

3.4 Boundary teaching UX

WorkspaceBoundaryHook is registered as an INTERCEPT pre-write hook scoped to /proc/{pid}/workspace/{...}. It compares the caller's agent_id to the workspace owner derived from the path (pid → AgentRegistry.lookup(pid).name). On mismatch the hook returns Err(EPERM) with a structured payload:

EPERM at /proc/p_scode/workspace/projects/nexus/src/main.rs:
  This workspace is owned by agent 'scode-standard' (pid p_scode).
  You are 'human-ethan'. To send a message about this workspace, write to:
     /proc/p_scode/workspace/chat-with-me
  (DT_LINK to /proc/p_scode/chat-with-me.)

The error is intentionally instructive. LLMs that hit it once learn the convention without memory or system-prompt edits.

3.5 Same primitive across humans and agents

/agents/human-ethan/chat-with-me is the canonical address — "human" identities have no spawn lifecycle so the path resolves directly to a long-lived DT_STREAM, no pid indirection needed.

3.6 Addressing non-human agents

Non-human agent names can map to zero, one, or many running pids in parallel. The chat-with-me surface for these agents is per-pid:

  • /proc/{pid}/chat-with-me — direct DT_STREAM at the per-pid path.
  • /proc/{pid}/workspace/chat-with-me — DT_LINK to the same stream.

3.7 Message contract

A mailbox envelope is a JSON object: the substrate manages the reserved from field (§3.3) and the participants agree on the payload. A2A payloads follow a shared contract so a receiver can act on a message from its content alone. A task assignment (copilot → worker) carries at least three parts:

  • context — what the task is and the state it starts from.
  • constraints — the bounds the worker operates under (for example, complete within a 200K-token budget).
  • acceptance — the criteria the result is judged against, carried in the envelope so the worker and the accepting copilot share one definition of done.

The copilot both issues the task and accepts the result; putting acceptance criteria in the message aligns the worker to that bar rather than leaving it implicit.

4. Cross-instance Transport

Two layers compose. Within a federation, raft replicates the chat-with-me DT_STREAM across every nexus instance. Outside the federation, a Matrix Client-Server adapter exposes the same DT_STREAMs over Matrix REST so unmodified third-party clients (Element, FluffyChat, Cinny) can join conversations.

4.1 Federation-internal — raft replication

Every chat-with-me DT_STREAM lives inside its zone's raft cluster. The write path is sys_write → WalStreamCore → Command::AppendStreamEntry → raft commit → state-machine apply on every voter.

The stream is a linearizable log: the state machine assigns each entry's offset at the raft apply, in committed order — the caller passes only the stream, never a sequence number. Because raft serializes every writer through one log, two agents writing the same mailbox (a follower's write forwards to the leader) land at distinct, gap-free offsets and every replica converges to one byte-identical ordered log — no writer can overwrite another. A write returns the offset it was assigned; a reader reads from an offset; the application never tracks sequence numbers. Being an ordered log, the mailbox is strong-consistency: a write needs a raft quorum (a total order needs a single sequencer), so a fully-isolated writer with no reachable quorum fails loud rather than silently accepting an unorderable write. Order-agnostic mutable state (presence, liveness) uses an eventually-consistent metadata register instead — never the stream.

4.3 Properties retained across both layers

  • Permissions — ReBAC on the DT_STREAM path governs who may write/read. Matrix room membership is derived from the same ReBAC decision.
  • Audit — Every Matrix-originated write reaches the kernel through sys_write, so AuditHook captures it like any other VFS write.
  • Single SSOT — The DT_STREAM is authoritative. None of the three clients maintain a parallel store.

7. Messenger Surface

Three clients sit over the same chat-with-me DT_STREAMs:

  • sudowork chat UI — talks gRPC directly to nexus.
  • Stock Matrix clients (Element, FluffyChat, Cinny) — connect to the Matrix C-S adapter over HTTP.
  • sudocode agent tasks — in-process tokio tasks read/write via direct kernel syscalls.

The chat-with-me DT_STREAM is the SSOT. None of the three clients maintain a parallel inbox.

8. Orchestration & Isolation Boundary

8.1 Orchestration lives outside nexus

nexus is passive VFS infrastructure: it stores state, routes syscalls, and fires hooks. Deciding which workers exist is an orchestrator concern.

8.2 Isolation

Agent loops share nexusd-cluster's address space as in-process loops. Isolation floor is catch_unwind per loop plus SpawnHandle::abort on reap. Workers are cattle: persistent state lives in /agents/{name}/, so a host that dies is restarted and each worker resumes from its --session-id transcript.

8.3 One nexus per host

A host runs exactly one kernel. The nexus-bootstrap launcher protocol owns discover-or-launch (PID file, ready file, socket path, health check).

8.4 Binary-edge placement

The binary that links both source trees is nexusd-cluster (rust/nexusd, nexus repo): it composes the nexus-vfs cluster boot + the nexus service crates and pulls sudocode_runtime as a library. Placing the link at this binary edge keeps the reusable crates (kernel, services, cluster) agent-runtime-free — they know only the SpawnTask DI trait — so the single nexus → sudocode edge is a binary leaf and never forms a cycle (sudocode_runtime depends only downward on kernel). scode stays a standalone CLI; the daemon (nexusd-cluster) is the host.
