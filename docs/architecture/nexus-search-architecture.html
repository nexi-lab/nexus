1. Layer overview

Search is a 4-layer stack. Layer boundaries are enforced by the plugin ABI (§2 below): the Rust core plugin only sees the kernel VFS through KernelHandle's C-ABI, and the orchestration/API layers only see the plugin through gRPC. No cross-layer imports.

2. Rust core plugin — SSOT for search logic

nexus-search-plugin is a cdylib loaded by nexusd-cluster at boot via --plugin-dir. It exposes nexus.search.v1.SearchService through the Phase P plugin-as-gRPC-service routing path (plugin declares its service list via nexus_plugin_grpc_services; the cluster's PluginProxyService routes external tonic traffic at /nexus.search.v1.SearchService/<Method> into nexus_service_dispatch).

SSOT status: in the cluster deployment profile (production), the Rust plugin is the sole search backend. Every algorithm below runs here, not in Python. The in-process SANDBOX indexing chain has been removed; workspace discovery remains in Python (§8).

2.2 Why plugin, not kernel primitive

Grep + glob are compositions over the kernel's sys_readdir + sys_read primitives, not primitives themselves. Putting the walker + regex engine + FTS + vector into the kernel tier would grow kernel/ with policy code that has no business next to the syscall ABI. The cdylib boundary keeps the kernel small (default: zero search logic) and lets the plugin ship its own release cadence with its own signed release chain.

2.3 Middleware layering (per-request)

4. HTTP surface

4.1 Python FastAPI in mixed deployments

Router: src/nexus/server/api/v2/routers/search.py. The Python server still serves /api/v2/search/query, query batching, glob/grep, health/stats, and indexed-directory management. Indexed queries use the Rust plugin; Python still adapts results and handles its own callers.

4.2 Rust axum in the cluster

Crate: nexus-vfs/rust/http-api/. The cluster installs this listener through rust/profiles/cluster/src/authorization.rs. Current routes:

  • GET /v2/status
  • GET /v2/search/glob and GET /v2/search/grep
  • POST /v2/search/query, including Rust cross-zone dispatch
  • POST /v2/documents/{index,refresh,batch} and GET /v2/documents/stats
  • GET/POST /v2/auth/keys and DELETE /v2/auth/keys/{key_hash}
  • GET/POST/DELETE /v2/rebac/tuples

The HTTP listener requires --enable-rebac and binds to loopback for use behind a TLS reverse proxy. It shares the daemon's auth provider, Raft API-key and tuple stores, readiness gate, and TLS identity. HTTP search preserves the incoming bearer credential when calling the gRPC host. That host enforces zone and file access, including on cached search results.

HTTP and gRPC coexist: the remote filesystem transport migrated from HTTP/JSON-RPC to gRPC; R10 retains an HTTP entry point and moves its implementation into Rust. HTTP adds request/response translation rather than another search backend or credential store.

nexus search query, index, and stats call the Rust HTTP listener. CLI glob/grep still use Python SearchService. See deployment and CLI setup.

5. Cross-zone federation dispatcher

The Rust dispatcher is implemented in nexus-vfs/rust/federated-search/, with shared delegation and routing types in rust/search-common/. The axum query handler uses the caller's readable zones and dispatches through local or remote backends before fusing results with RRF. Remote legs use SearchDelegation; the receiving host enforces the delegated scope.

The Python federated_search.py remains reachable from the Python HTTP router. Its continued existence is caller-migration work, not a missing Rust dispatcher. See the completed port and its design history.

Layer contract: cross-zone orchestration, zone discovery, and delegation belong in services outside the core plugin. The plugin owns search primitives and same-zone peer fan-out. The gRPC host owns caller authentication and permission enforcement.

6. Search over DT_STREAM (audit / mailbox / transcripts)

A DT_STREAM is a kernel-primitive append-only log — audit trails, A2A mailboxes, session transcripts (see the Integration Architecture doc §4.2 for the primitive). As of nexus-vfs #229 + nexus #4682, streams are searchable as first-class documents: grep, keyword Query, and semantic Query all see a stream's whole log the same way they see a regular file.

6.1 How it works — the “host-shim collects” posture (Phase 0)

The plugin's C-ABI sys_read is offset-less — it means “give me the content at path”. For DT_REG this is the file bytes. For DT_STREAM the host-side (nexus-vfs #235) now walks the stream frames to its tail and returns the deframed payload as one blob. Zero plugin-abi bump. The plugin's existing walker (which already routes DT_REG → chunk → index) just needs to recognise DT_STREAM=4 as a searchable entry_type.

The plugin change (PR #4682, merged) added exactly one SSOT predicate:

fn searchable_content_type(et: u8) -> bool { et == DT_REG || et == DT_STREAM }

Routed through all 5 VFS-walk gates: grep, keyword-index (recursive + non-recursive), semantic-index (recursive + non-recursive). DT_DIR/DT_MOUNT stay containers; DT_PIPE stays ephemeral (destructive read).

6.2 Verification

TestSearchStreams in tests/e2e/docker/test_search_plugin.py seeds a 7-frame wal stream whose target token sits in the 6th frame plus a sibling regular file. It asserts:

  • grep finds the LATE-frame token in the stream (proves the host read the whole log, not frame 0)
  • grep also finds the early-frame token + the sibling file's token (no regression)
  • keyword index + Query surfaces stream content as a document
  • semantic Query works too (tolerant of a missing embedder)

6.4 Client path for a co-hosted Rust agent calling Query

Today's answer has a gap:

  • Grep / glob: in-process via KernelConvenience::grep_subtree (already there).
  • Semantic / hybrid Query: no in-process convenience. Two options today:
    1. tonic client to local plugin gRPC (loopback) — same pattern the Rust http-api crate uses in SearchBackend. Recommended short-term.
    2. Add KernelConvenience::semantic_search in nexus-vfs — long-term, needs kernel-team review because it crosses the plugin/convenience boundary (grep_subtree precedent exists but semantic requires embedder wiring in kernel tier).

7. R10 pure-Rust migration arc

Epic issue #4674. Goal: production nexus-server runs on the cluster Rust binary alone — HTTP + auth + ReBAC + orchestration all move from Python to Rust, keeping the plugin unchanged as the SSOT for search primitives.

Landed capabilities

  • Rust HTTP search/document routes, bearer middleware, API-key management, and ReBAC tuple management.
  • Rust ReBAC and Raft tuple storage; Rust cross-zone dispatcher and delegation.
  • Production cluster composition sharing auth, ReBAC, TLS channels, and readiness across HTTP and gRPC.
  • SANDBOX in-process indexing-chain removal; the Rust plugin owns indexed query and stats.
  • Indexed Search CLI on Rust HTTP, verified with the published signed-plugin image, real credentials, isolation, and revocation.

Remaining work

  • Migrate and verify remaining Python callers, including CLI glob/grep and the Python HTTP query/federation paths, before deleting SearchService and its adapters.
  • Resolve Graph and Zoekt feature coverage before removing their Python integrations.
  • Resolve the epic's session-cookie requirement before retiring Python auth routes; the Rust HTTP middleware currently accepts bearer credentials.
  • Prove the Rust deployment in a real production tenant before retiring nexus-server, as required by the epic.

Passing the current CLI and published-image gates completes those increments; it does not close the whole migration epic.
