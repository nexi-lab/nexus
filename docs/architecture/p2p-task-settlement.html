P2P AI-Assisted Micro-Task Settlement DRAFT v1.4

A peer-to-peer task dispatch and settlement protocol for sudowork, built on nexus-vfs primitives.
Every seller has an AI copilot. Every task is an opportunity to learn AI-assisted work.

Why this matters

This is not just a micro-task platform. It's a vehicle for AI-assisted labor adoption at scale.

Today, AI tools are primarily used by knowledge workers. Most of the workforce has never experienced AI augmentation in their daily work. This platform changes that: sellers earn money completing micro-tasks, and in the process, they learn to collaborate with an AI copilot — understanding tasks, generating content, producing proof of work. The skills they develop — prompt crafting, AI-assisted writing, tool delegation — transfer directly to their own careers.

The economic incentive (earning points) funds the education (learning AI-assisted work). The platform simultaneously solves the buyer's need for scalable task completion and the seller's need for accessible AI skill-building. This is meaningful at a societal level: lowering the barrier to AI adoption for the broader labor force, not just the tech elite.

Value to sudowork's existing collaboration network

Beyond new market creation, P2P task settlement strengthens sudowork's core product thesis: the 1% peer-to-peer collaboration network. Today, sudowork enables multi-agent collaboration across companies and domains — but not all collaboration happens within a company. Open-source contributors, nonprofits, freelance experts, and cross-org working groups all collaborate without shared payroll. These collaborations lack an economic incentive layer: there's no native way to settle a code review, a design critique, or a research contribution between two sudowork instances that belong to different organizations.

P2P task settlement fills this gap. It turns sudowork's collaboration network from "we can work together" into "we can work together and settle payment trustlessly". This creates a new incentive for the 1% peer network: every new participant is not just a collaboration partner but a potential buyer or seller of micro-tasks. The network effect compounds — more participants means more task liquidity, which attracts more participants.

Agent-native matching vs traditional RTB

Online advertising uses Real-Time Bidding (RTB): a 3rd-party exchange matches buyer and seller in ~100ms. This system works for ads but fails for labor — the platform controls all matching power, takes a large rake, and has no understanding of task content. Agent-native matching is fundamentally different:

DimensionRTB (traditional)Agent-native (sudowork)
Matching powerCentralized exchange (platform decides)Buyer & seller agents negotiate directly (P2P)
Task decompositionImpossible — platform doesn't understand task contentAgent decomposes complex tasks into micro-tasks (understands content)
Verification3rd-party platform, limited visibilityLocal agent verifies (L1 trust zone, full content access)
Task granularityCoarse (one ad impression = one unit)Fine-grained → better liquidity (agent can split/merge)
Seller learningNone — seller is a passive slotAgent teaches seller AI skills through collaboration

The seller's agent learns preferences over time. Unlike RTB's cold matching where every impression is independent, sudowork accumulates knowledge about its human: what tasks they excel at, preferred working hours, quality patterns, domain expertise. This local learning (entirely within L1) means task selection improves with use — the agent becomes a better advocate for its human, not just a task router.

LayerWhoTrust LevelDesign Implication
L1: My Trust Zone Me ↔ My sudowork Complete Runs locally, acts 100% in my interest. I paid for the points, my AI is my agent. All secrets, strategies, acceptance logic stay local.
L2: Peer Zone My sudowork ↔ Their sudowork Zero Counterparty could cheat. Need cryptographic signatures, hash commitments. Every message must be verifiable. No shared state without proof.

Design Principle

Minimize L3 (server) involvement. Maximize L1 (local) intelligence. Make L2 (peer) interactions cryptographically verifiable. The server is a witness, not an arbiter.

3. AI as Advocate (Trust Zone Alignment)

Interest Alignment Principle

Each sudowork instance is fully aligned with its human's interest. The human paid real money for the points powering that sudowork — so the AI and the human are economically bound.

  • Buyer's sudowork: optimizes for quality verification, fair pricing, detecting incomplete work
  • Seller's sudowork: optimizes for meeting acceptance criteria efficiently, advocating for fair compensation, protecting against unreasonable rejection

This adversarial alignment is by design — it produces fair outcomes the same way buyer/seller negotiation does in real markets.

5. The Escrow Problem

Points live on sudoprivacy's server. Settlement must touch the server. The question: how much power does the server have?

Option A: Server-Held Escrow

How: Buyer calls server.lock(amount, contract_hash). Server holds points until server.release() or timeout.

Pro: Seller has guarantee — points locked, buyer can't spend elsewhere.

Con: Server has unilateral release power. Buyer could hack release API. Compromised server = stolen funds. Contradicts L3 (limited trust).

Option B: Dual-Signature Settlement (no server escrow) ☆ preferred

How: No escrow. On acceptance, buyer signs a release(contract_id, amount, to_seller) message. Seller submits (release_msg + buyer_sig + seller_sig) to server's transfer API. Server verifies both signatures, executes transfer.

Pro: Server is a signature verifier, not a decider. Can't forge signatures. Can't move funds unilaterally. Minimal trust.

Con: Buyer can refuse to sign (hostage problem). Mitigated by timeout + reputation.

Option B + Pre-commitment (see below). Server as verifier aligns with L3 (limited trust).

Option B+: Buyer Pre-commitment (addresses low-trust markets)

Problem: In low-end labor markets, reputation is weak. Buyer can refuse to sign the release (hostage problem). "Timeout + reputation" is insufficient when participants have no reputation to lose.

Solution: When both parties sign the contract (agreed), buyer also signs a conditional release:

  {
    "type": "conditional_release",
    "contract_id": "...",
    "amount": 500,
    "to_seller": "seller_user_id",
    "condition": "delivery_submitted AND NOT rejected_within_timeout",
    "timeout_hours": 72,
    "buyer_signature": "ed25519:..."
  }

This pre-signed message is stored on the server at contract creation time.

Settlement paths:

  • AI auto-accepts → buyer's AI checks criteria, signs explicit release → immediate transfer (no human wait)
  • AI or human rejects → must actively reject before timeout with reason → seller can revise
  • No response for 72h → server executes pre-signed conditional release automatically
  • Human async override → human can intervene at any point before timeout (local preference, e.g. "notify me for contracts >100 points")

Key insight: Server still isn't an arbiter — it only executes a commitment the buyer already signed. No unilateral power. The buyer bound themselves at contract creation time.

Clarification: The timeout_hours value is NOT set by the server. It comes from contract.terms.auto_accept_timeout_hours, which is negotiated and agreed upon by both buyer and seller before signing. The server merely reads the timeout from the buyer's pre-signed conditional release — it makes zero business decisions.

Option C: Hash-Locked Transfer (HTLC-inspired)

How: Buyer creates hash-locked commitment: "pay N points to whoever reveals preimage of H". Seller delivers + reveals preimage. Automatic.

Pro: Atomic — delivery and payment cryptographically linked.

Con: Only works for objectively verifiable deliverables (file hash). Can't handle quality verification ("labeled but poorly"). Overly complex.

Option D: Reputation-First (MVP fallback)

How: No escrow, no crypto. Buyer pays after acceptance via transfer API. Trust from reputation + signed contract history.

Pro: Simplest. No server changes. Works for trusted communities.

Con: No guarantee. Only works with social trust.

Recommendation

Start with Option B (dual-signature). It's not much harder than D, but provides real cryptographic guarantees. Server needs only one new endpoint: POST /transfer that verifies dual signatures. Option D as fallback for communities that don't need formal contracts.

5A. Reputation System (reuse from nexus)

Nexus previously had a full reputation service (deleted in PR #2600 as dead code, 759 lines). The math model is well-designed and directly reusable.

Prior art: Bayesian Beta reputation model

reputation_math.py (deleted, recoverable from git)
  • Model: Beta(alpha, beta) distribution per dimension. score = alpha / (alpha + beta). Prior Beta(1,1) = 0.5 (no information).
  • 4 dimensions: reliability (30%), quality (30%), timeliness (20%), fairness (20%) — weighted composite.
  • Time decay: Exponential with 30-day half-life. Recent events weigh more.
  • Confidence: Logarithmic scale — 0 observations = 0.0, 10 obs = 0.71, 100 obs = 0.82.
  • Federation-safe: No process-local caches. Reads go to storage directly.

Role in the system: marketplace signal, NOT settlement enforcement

Two independent mechanisms, two different problems
MechanismSolvesNature
Pre-commitment + dual-sig (§5)This transaction won't be cheatedHard guarantee (cryptographic)
Reputation (§5A)Pick a reliable counterparty next timeSoft signal (statistical)

Reputation does not participate in settlement logic. It doesn't gate payments, doesn't override pre-commitments, doesn't resolve disputes. It's a dashboard metric visible on the marketplace — helps buyers choose sellers and sellers choose buyers. The two systems are intentionally decoupled.

Bilateral: both buyer AND seller are rated

DimensionRating SellerRating Buyer
Reliability (30%)Delivers on time, doesn't ghostResponds to delivery on time, doesn't ghost
Quality (30%)Deliverable meets acceptance criteriaRequirements are clear and fair
Timeliness (20%)Completes before deadlineAccepts/rejects within timeout
Fairness (20%)Reasonable pricing, honest workDoesn't maliciously reject, doesn't underpay

Buyer reputation matters as much as seller reputation — sellers need to know if a buyer is trustworthy before accepting a task. Same model as ride-sharing (driver rates passenger, passenger rates driver).

Adaptation for P2P task settlement

AspectOriginal (deleted nexus code)Adapted
Who rates whomAgent → AgentAgent → Agent, bilateral (both buyer and seller rated)
StoragePostgreSQL (RecordStore)VFS files (JSON, CAS-addressed) — everything is a file
DistributionFederation-safe (database reads)Inherits nexus-vfs Raft consensus for replicated reputation data

VFS storage layout
  /reputation/{user_id}/score.json       # materialized composite score
  /reputation/{user_id}/events/           # individual feedback events (append-only)
  /reputation/{user_id}/events/{event_id}.json

Each event is CAS-addressed — tamper-evident. Composite score is recomputable from events.

Agent rates on behalf of human (L1 alignment)

The agent submits feedback on behalf of its human. This is not autonomous AI scoring — the agent acts within the L1 trust zone, aligned with its human's interests (the human paid for the points powering the agent).

How much the human reviews vs delegates to the AI is a local preference: some users will review every rating, others will let their AI handle routine feedback. This alignment process is entirely within L1 — out of protocol scope. The protocol only requires that feedback is signed by the agent's key, which the human controls.

Reuse reputation_math.py pure functions (Beta scoring + time decay + composite). Replace ORM with VFS JSON. Bilateral rating (buyer + seller). Reputation is a marketplace signal only — does not gate settlement.

7. Scenarios

Two real-world scenarios that stress-test different aspects of the protocol.

Scenario A: Data Labeling (with real production data)

Buyer: "Label 1000 images for object detection. Bounding boxes in COCO format. 500 points."

Seller: Data labeler. Their sudowork runs the labeling pipeline (model selection, detection, classification), seller does quality review.

Acceptance criteria:

  • All 1000 images labeled (count check — machine-verifiable)
  • COCO JSON format valid (schema check — machine-verifiable)
  • Accuracy > 95% on 50-image spot check (quality check — AI-assisted, human-confirmed)

Delivery: COCO JSON + labeled images in VFS. CAS hash covers the entire dataset.

Real data point: UI element labeling (June 2026)

Production data from a desktop-use annotation pipeline. Full AI: OmniParser detection → YOLO → Claude Opus 4.6 reclassification.

Stress tests:

  • Verification: Mix of machine-verifiable (count, format) and subjective (accuracy) criteria. Buyer's AI can automate the first two; spot-check needs AI + human.
  • Volume & task decomposition: 81K elements in a single contract may be too large — seller's agent evaluates ROI and may decline. Buyer's sudowork can split into ~21 contracts of 100 images each. Granularity is buyer agent's L1 decision.
  • Template contracts: For standard task types like "UI labeling", buyer's sudowork can use pre-defined templates that skip negotiation. Seller agent sees "UI labeling, 100 images, 30 points, 72h timeout" and accepts/rejects instantly. Whether to use templates is the buyer agent's decision (L1), not platform-mandated.
  • Pipeline as product capability: The seller does not build their own pipeline. Sudowork provides OmniParser+model orchestration as a product-level capability. Seller says "label these images", sudowork handles the rest. sudowork product team must keep pace with pipeline capabilities for key task types.
  • Seller specialization: A seller who completes many labeling tasks can fine-tune a local model (if they have GPU, e.g. DGX) on accumulated task data, increasing accuracy over time → higher reputation → more tasks at higher prices (positive feedback loop). Without GPU, sudowork's model choice meta-learning remembers which model works best for which task type — lightweight specialization for all sellers.
  • Partial quality: What if 900/1000 are good but 100 are sloppy? Revision or partial payment?

Scenario B: Social Media Engagement (Douyin)

Buyer: Brand/creator wants organic engagement. "Visit my Douyin profile, browse 3+ videos, follow if interested, like 1-2 videos, leave a genuine comment. 10 points."

Seller: Real person with a Douyin account. Their sudowork guides them through the task.

Acceptance criteria:

  • Profile visited (screenshot or interaction proof)
  • ≥3 videos watched (view duration proof)
  • Follow action completed (follower count delta or screenshot)
  • 1-2 likes placed
  • 1 genuine comment left (not spam, contextually relevant)

Delivery: Interaction proof bundle (screenshots, timestamps) in VFS.

Stress tests:

  • Non-reversibility: Unlike code, the seller can't "un-follow" easily. The work has real-world side effects. Even if the seller loses interest later, the follow/like probably persists — buyer gets long-term value.
  • Proof of action: How to prove the engagement happened? Screenshots can be faked. Need to think about attestation — perhaps browser automation logs from sudowork's ai-dev-browser?
  • Genuine-ness: The comment must be "genuine" — this is inherently subjective. Buyer's AI can check if the comment is contextually relevant to the video content, but ultimately human judgment.
  • Interest alignment: If the seller genuinely finds the content interesting, they become a long-term follower (win-win). If not, they still did the task but won't engage further. Either outcome is acceptable — the buyer is paying for initial exposure, not permanent commitment.
  • Micro-task economics: 10 points per task = very small. Need efficient contract negotiation (templates?) and low-friction settlement. Can't have heavyweight crypto for micro-payments.
Design implications from scenarios
  • Mixed verification: Protocol must support both machine-verifiable and human-judged criteria, explicitly marked in the contract.
  • Proof types: Different tasks need different proof mechanisms — CAS hash for data files, screenshots/logs for actions. Protocol should be proof-type-agnostic.
  • Micro-task support: Scenario B (10 points) needs lightweight contracts. Perhaps template-based "task types" to skip negotiation for standard tasks.
  • Non-digital side effects: Some deliverables (social engagement) have real-world consequences that outlive the contract. Interesting but not a protocol-level concern.

7A. Economics: End-to-End Cost Model

Using Scenario B (Douyin engagement) as the reference micro-task. Prices in CNY.

Positioning: AI-Assisted Micro-Task Platform

This is not just another crowdsourcing platform. The differentiator: every seller has an AI copilot (sudowork) that helps them understand tasks, execute efficiently, and generate delivery proofs. This lowers the skill floor — more people can do more types of work — and raises quality (AI pre-checks deliverables before submission).

The platform simultaneously serves as an adoption vehicle for AI-assisted labor: sellers who start using sudowork for micro-tasks naturally discover its value for their own work, driving organic growth.

AI Assistance: Seller's Investment Decision

The seller's AI tokens are the seller's own investment, not the platform's cost. How much AI help to use is a local optimization within the seller's L1 trust zone:

  • High-skill seller: Does most work manually, uses AI minimally (saves tokens, keeps more profit)
  • Low-skill seller: Relies heavily on AI guidance (spends more tokens, but can complete tasks they otherwise couldn't)
  • Model choice: Each seller picks their own model. Simple tasks → DSV4 or similar cheap model. The protocol doesn't mandate a model.

This creates a natural market for AI-assisted labor: the platform makes AI assistance accessible and economically viable for micro-work, driving adoption.

Points Liquidity: Stable-Price Buyback

Sellers earn points but need real currency. sudowork offers a stable-price buyback at 5-10% of the original charge price.

  • Framing: "refund" or "credit redemption" — not "exchange" or "withdrawal" (avoids financial instrument classification)
  • Mechanism: Seller requests buyback → sudoprivacy credits the amount to seller's payment method at the published buyback rate
  • Rate example: Charge rate ¥1 = 100 points. Buyback rate: 100 points = ¥0.05-0.10
  • Policy risk: Needs legal review. Framing as "partial refund of unused credits" rather than "currency exchange" is safer. Many game platforms (Steam, Apple) have similar credit refund mechanisms.

Note: Buyback rate and policy details require legal consultation before launch. Recorded here as design option.

Why tokens are worth more than cash to sellers

The buyback rate (5-10%) creates a 10-20x leverage effect that naturally drives AI adoption:

Cash out (buyback) 50 points from task ¥0.025-0.05 cash 0.05-0.1x face value

The economics: Model provider subsidies (e.g. DSV4 pricing) mean the platform's actual compute cost is far below the charge rate. This cost gap is passed to sellers as amplified AI value — 50 points buys ¥0.50 of AI compute that costs the platform perhaps ¥0.05. The buyback rate (¥0.025-0.05) roughly matches the platform's real cost, so it's sustainable.

The flywheel: Sellers who use points for AI get 10-20x more value than cashing out → they learn AI skills → they discover AI's value for their own work → they buy their own points → organic growth. The economic incentive and the education mission are the same mechanism.

Critical assumption: This leverage only works if AI is genuinely useful to sellers. If sellers can't find value in AI-assisted work, they'll want to cash out (and get very little). The platform must ensure sudowork delivers real value in the seller's L1 trust zone — task understanding, skill development, career-transferable AI literacy.

Target Market: University Students & Fresh Graduates (China)

Initial seller pool: university students and fresh graduates (大学生/应届生). This demographic is uniquely aligned with the platform on multiple dimensions:

DimensionWhy it aligns
Supply volumeChina's university enrollment is at a historic high (~11.7M graduates in 2025), while youth employment rates are at historic lows. Largest available micro-task labor pool.
AI willingnessDigital natives, highest willingness to learn and use AI tools. Crucially: more willing to accept tokens as compensation because they'll actually use the AI — the 10-20x leverage (use vs cash out) works best for users who value AI access.
Time flexibilityFlexible schedules, can do micro-tasks between classes or during free time. Ideal for async, variable-volume task flows.
Low opportunity costStudent wages are low; ¥4-10/hour effective rate from micro-tasks is competitive with part-time alternatives (tutoring, food delivery).
Maximum career ROIAI skills learned now compound over an entire career. A graduating student who can prompt-craft, delegate to AI, and verify AI output has a tangible competitive advantage in the job market.
Network effectsCampus social networks drive organic word-of-mouth. One student showing AI-assisted earnings to roommates creates viral adoption within dorms and departments.

The pitch to students: "Earn money doing micro-tasks. Your AI copilot helps you work faster and learn skills employers want. The points you earn buy more AI — 10-20x more value than cashing out."

AI value varies by scenario. The table below maps where AI helps most — at the transaction layer (negotiation, verification, settlement) vs the execution layer (doing the actual work).

Data labeling (Scenario A) High — auto-verify format, spot-check accuracy High — AI pre-labels, human corrects AI adds value at both layers. Strongest use case.
Social engagement (Scenario B) High — auto-verify screenshots, comment relevance Medium — AI drafts comment, human performs action Execution is physical (app interaction); AI assists but can't replace.

Design implication: The protocol is task-type-agnostic, but the platform guidance should steer sellers toward task types where AI leverage is highest — maximizing both earnings efficiency and AI skill development.

8. Open Questions

Resolved items removed in v0.9: "Timeout on buyer non-response" (→ §5 B+, contract-negotiated auto-accept), "Multi-revision contracts" (→ §4, agent-to-agent negotiate max_revisions, no platform limit).

  1. Escrow model: Start with B (dual-signature) or D (reputation)?
    Start with B. The server API cost is one endpoint (POST /transfer with signature verification). Reputation alone (D) is too weak for strangers. B gives real guarantees from day one.
  2. Dispute resolution: P2P reputation or platform arbitration?
    P2P reputation for v1. Platform arbitration is a v2 feature that requires sudoprivacy to build an arbitration team/process. Signed contracts + audit logs provide evidence if disputes escalate outside the system.
  3. Points transfer API: Does sudoprivacy already support user-to-user transfers?
    Confirmed: no transfer API exists. Current system is charge (pay sudoprivacy) and consume (use LLM) only. Need new endpoint: POST /api/v1/transfer with dual-signature verification. The transfer must accept (release_msg + buyer_sig + seller_sig), verify both Ed25519 signatures against the contract terms, and atomically move points between accounts. Minimal surface — one new endpoint, no escrow state.
  4. Discovery / Marketplace: How do buyers find sellers?
    Direct P2P for v1 (buyer sends contract offer to a known seller). Marketplace is a v2 feature. Confirmed: no marketplace code exists in nexus (checked git history). Need to build from scratch — task listing, search, seller profiles, category taxonomy. This is a significant build, separate from the settlement protocol.
  5. Partial delivery / milestone payments: Split large tasks?
    v2. For v1, one contract = one deliverable = one payment. Large tasks can be manually split into multiple contracts. Milestone support adds complexity (partial signatures, partial releases) that isn't needed for MVP.
  6. Cross-platform: Seller uses non-sudowork tools (browser, Douyin app, labeling tools)?
    Not "both parties must use sudowork" — rather, integrate external task tools into sudowork via MCP servers and ai-dev-browser. The seller's sudowork orchestrates: it drives the browser for Douyin interactions, launches labeling tools, captures screenshots — all within the seller's L1 trust zone. The protocol still requires sudowork-to-sudowork communication (L2), but the execution tools are extensible. MCP makes this plug-and-play: each new tool type is just a new MCP server, no protocol changes needed.
  7. Points buyback mechanism: How do sellers convert earned points to real currency?
    Stable-price buyback at 5-10% of original charge price (see §7A). Key open items: (a) legal classification — "partial refund" framing vs "currency exchange" risk, needs legal review; (b) buyback rate stability — fixed rate or floating with usage metrics; (c) minimum threshold — avoid micro-withdrawals that cost more to process than they're worth; (d) frequency limits — daily/weekly caps to manage cash flow. Policy risk is real: if regulators classify points as a financial instrument, compliance burden increases significantly. Precedent: Steam Wallet, Apple App Store credits have similar refund mechanisms.
