1. Three-Layer Trust Model

Every participant sees the same three trust layers. The diagram is drawn from your perspective — you could be either Buyer or Seller. The counterparty is always "them".

Example: If I'm the Buyer posting a data-labeling task, then "My sudowork" helps me draft the task and verify deliverables. "Their sudowork" is the Seller's agent that does the work. Roles are symmetric — if I'm the Seller, the diagram flips.

LayerWhoTrust LevelDesign Implication
L1: My Trust Zone Me ↔ My sudowork Complete Runs locally, acts 100% in my interest. I paid for the points, my AI is my agent. All secrets, strategies, acceptance logic stay local.
L2: Peer Zone My sudowork ↔ Their sudowork Zero Counterparty could cheat. Need cryptographic signatures, hash commitments. Every message must be verifiable. No shared state without proof.
L3: Platform Me ↔ sudoprivacy server Limited I deposited money (bought points). Server holds the ledger. I want it to be a witness/verifier, not a decider. It should not have unilateral power over my funds.
Design Principle

Minimize L3 (server) involvement. Maximize L1 (local) intelligence. Make L2 (peer) interactions cryptographically verifiable. The server is a witness, not an arbiter.

2. Roles: Buyer & Seller

RoleWhoWhat they do
Buyer (买家) Posts and pays for the task Defines task, acceptance criteria, price. Their sudowork assists with verification.
Seller (劳动者/卖家) Does the work Accepts the task, executes, delivers. Their sudowork assists with execution and advocates for fair payment.

Both roles are symmetric in trust structure: each has their own L1 trust zone, and the other party is always L2 (zero trust).

3. AI as Advocate (Trust Zone Alignment)

Interest Alignment Principle

Each sudowork instance is fully aligned with its human's interest. The human paid real money for the points powering that sudowork — so the AI and the human are economically bound.

  • Buyer's sudowork: optimizes for quality verification, fair pricing, detecting incomplete work
  • Seller's sudowork: optimizes for meeting acceptance criteria efficiently, advocating for fair compensation, protecting against unreasonable rejection

This adversarial alignment is by design — it produces fair outcomes the same way buyer/seller negotiation does in real markets.

AI involvement at each stage:

5. The Escrow Problem

Points live on sudoprivacy's server. Settlement must touch the server. The question: how much power does the server have?

Option A: Server-Held Escrow

How: Buyer calls server.lock(amount, contract_hash). Server holds points until server.release() or timeout.

Pro: Seller has guarantee — points locked, buyer can't spend elsewhere.

Con: Server has unilateral release power. Buyer could hack release API. Compromised server = stolen funds. Contradicts L3 (limited trust).

Option B: Dual-Signature Settlement (no server escrow) ☆ preferred

How: No escrow. On acceptance, buyer signs a release(contract_id, amount, to_seller) message. Seller submits (release_msg + buyer_sig + seller_sig) to server's transfer API. Server verifies both signatures, executes transfer.

Pro: Server is a signature verifier, not a decider. Can't forge signatures. Can't move funds unilaterally. Minimal trust.

Con: Buyer can refuse to sign (hostage problem). Mitigated by timeout + reputation.

Option B. Server as verifier aligns with L3 (limited trust). The "buyer refuses to sign" problem is solvable with timeout auto-accept + reputation damage, which are simpler than building a trustworthy escrow system.

Option C: Hash-Locked Transfer (HTLC-inspired)

How: Buyer creates hash-locked commitment: "pay N points to whoever reveals preimage of H". Seller delivers + reveals preimage. Automatic.

Pro: Atomic — delivery and payment cryptographically linked.

Con: Only works for objectively verifiable deliverables (file hash). Can't handle quality verification ("labeled but poorly"). Overly complex.

Option D: Reputation-First (MVP fallback)

How: No escrow, no crypto. Buyer pays after acceptance via transfer API. Trust from reputation + signed contract history.

Pro: Simplest. No server changes. Works for trusted communities.

Con: No guarantee. Only works with social trust.

Recommendation

Start with Option B (dual-signature). It's not much harder than D, but provides real cryptographic guarantees. Server needs only one new endpoint: POST /transfer that verifies dual signatures. Option D as fallback for communities that don't need formal contracts.

7. Scenarios

Two real-world scenarios that stress-test different aspects of the protocol.

Scenario A: Data Labeling

Buyer: "Label 1000 images for object detection. Bounding boxes in COCO format. 500 points."

Seller: Data labeler. Accepts, labels images (possibly with AI assistance), delivers labeled dataset.

Acceptance criteria:

  • All 1000 images labeled (count check — machine-verifiable)
  • COCO JSON format valid (schema check — machine-verifiable)
  • Accuracy > 95% on 50-image spot check (quality check — AI-assisted, human-confirmed)

Delivery: COCO JSON + labeled images in VFS. CAS hash covers the entire dataset.

Stress tests:

  • Verification: Mix of machine-verifiable (count, format) and subjective (accuracy) criteria. Buyer's AI can automate the first two; spot-check needs AI + human.
  • Volume: Large deliverable (1000 images). CAS chunking + federation handles transfer.
  • Partial quality: What if 900/1000 are good but 100 are sloppy? Revision or partial payment?

Scenario B: Social Media Engagement (Douyin)

Buyer: Brand/creator wants organic engagement. "Visit my Douyin profile, browse 3+ videos, follow if interested, like 1-2 videos, leave a genuine comment. 10 points."

Seller: Real person with a Douyin account. Their sudowork guides them through the task.

Acceptance criteria:

  • Profile visited (screenshot or interaction proof)
  • ≥3 videos watched (view duration proof)
  • Follow action completed (follower count delta or screenshot)
  • 1-2 likes placed
  • 1 genuine comment left (not spam, contextually relevant)

Delivery: Interaction proof bundle (screenshots, timestamps) in VFS.

Stress tests:

  • Non-reversibility: Unlike code, the seller can't "un-follow" easily. The work has real-world side effects. Even if the seller loses interest later, the follow/like probably persists — buyer gets long-term value.
  • Proof of action: How to prove the engagement happened? Screenshots can be faked. Need to think about attestation — perhaps browser automation logs from sudowork's ai-dev-browser?
  • Genuine-ness: The comment must be "genuine" — this is inherently subjective. Buyer's AI can check if the comment is contextually relevant to the video content, but ultimately human judgment.
  • Interest alignment: If the seller genuinely finds the content interesting, they become a long-term follower (win-win). If not, they still did the task but won't engage further. Either outcome is acceptable — the buyer is paying for initial exposure, not permanent commitment.
  • Micro-task economics: 10 points per task = very small. Need efficient contract negotiation (templates?) and low-friction settlement. Can't have heavyweight crypto for micro-payments.
Design implications from scenarios
  • Mixed verification: Protocol must support both machine-verifiable and human-judged criteria, explicitly marked in the contract.
  • Proof types: Different tasks need different proof mechanisms — CAS hash for data files, screenshots/logs for actions. Protocol should be proof-type-agnostic.
  • Micro-task support: Scenario B (10 points) needs lightweight contracts. Perhaps template-based "task types" to skip negotiation for standard tasks.
  • Non-digital side effects: Some deliverables (social engagement) have real-world consequences that outlive the contract. Interesting but not a protocol-level concern.

8. Open Questions

  1. Escrow model: Start with B (dual-signature) or D (reputation)?
    Start with B. The server API cost is one endpoint (POST /transfer with signature verification). Reputation alone (D) is too weak for strangers. B gives real guarantees from day one.
  2. Timeout on buyer non-response: Auto-accept or auto-refund after N hours?
    Auto-accept after 72h (contract-configurable). Rationale: seller did the work and delivered; buyer silence should not punish the seller. Buyer's AI will notify the human well before timeout.
  3. Dispute resolution: P2P reputation or platform arbitration?
    P2P reputation for v1. Platform arbitration is a v2 feature that requires sudoprivacy to build an arbitration team/process. Signed contracts + audit logs provide evidence if disputes escalate outside the system.
  4. Points transfer API: Does sudoprivacy already support user-to-user transfers?
    Likely not — current system is charge (pay sudoprivacy) and consume (use LLM). Need one new endpoint: POST /api/v1/transfer with dual-sig verification. Minimal surface.
  5. Discovery: How do buyers find sellers?
    Out of scope for v0.1. Start with direct P2P (buyer sends contract offer to a known seller). Marketplace/broadcast is a v2 feature. Focus on the settlement protocol first.
  6. Multi-revision contracts: How many rounds before auto-settle?
    Contract-level config with default max_revisions=2. After max revisions exhausted, buyer must accept or dispute — can't keep requesting changes indefinitely. Protects seller from scope creep.
  7. Partial delivery / milestone payments: Split large tasks?
    v2. For v1, one contract = one deliverable = one payment. Large tasks can be manually split into multiple contracts. Milestone support adds complexity (partial signatures, partial releases) that isn't needed for MVP.
  8. Cross-platform: Seller uses non-sudowork tool?
    Out of scope. Both parties must use sudowork for v1 — the protocol relies on local trust zone (L1) properties that only hold for sudowork instances. Cross-platform would need a standard protocol (A2A?) which is premature.
