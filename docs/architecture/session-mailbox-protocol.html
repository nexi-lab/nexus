One session driver: acp-mailbox/1

Both managed subprocesses and co-hosted engines expose the same conversation transport. ACP supplies the complete turn vocabulary; the A2A envelope supplies authenticated addressing and a channel generation. Clients use the shared NexusSessionTransport from the Nexus VFS Node SDK. Subprocess stdio belongs to the host adapter. There are no public session fd streams and no separate text-only co-host turn loop.

Identities and startup

ValueLifetime and purpose
Agent namePersistent mailbox identity; conversations are addressed by participant names.
Durable session IDTranscript identity across runs. ACP returns it from session/new. Co-host start also returns durable_session_id; resume_session_id selects it on the next start.
Process IDOne live run. The legacy managed_agent v1 field named session_id contains this ID. It is used only for get/cancel control calls, never to derive the conversation address.
channel_idOne attachment generation. A new start allocates a new generation even when restoring the same durable session.

managed_agent.start_session_v1 accepts {agent_id, model?, repos?, resume_session_id?, spawn_spec?}. A spawn specification selects the subprocess host; omitting it selects the installed in-process provider. Both return session_endpoint:

{
  "protocol": "acp-mailbox/1",
  "channel_id": "fresh-generation",
  "agent": "worker",
  "controller": "authenticated-caller",
  "transcript": "/conversations/<pair-id>/transcript"
}

The caller uses the supplied address. It must continue using the same authenticated actor as the start call. The server chooses controller from the delegated agent identity, or the authenticated user identity when no agent delegation exists. The write hook stamps from; body-authored identities are not authority. Auth-off deployments offer no identity guarantee. A provider that cannot return this endpoint is rejected. Clients reject old daemons and reap the just-created process instead of switching transports.

Open the mailbox, send ACP initialize (protocolVersion: 1), then session/new or session/load. In co-host mode the latter must name the session prepared by start_session. Peer messages remain queued until the controller opens the session. session/list lists live sessions. In-place co-host reset, cross-session load and fork are refused: a different durable identity needs its own start call and writer lease. sessionFork is advertised as false for this host.

Framing and ordering

Each authenticated StreamWrite appends exactly one JSON envelope to the framed conversation transcript. StreamReadAt returns one record and its next record offset. A regular byte file is not a session transport. Both directions share the transcript:

{
  "from": "authenticated-caller", "to": "worker", "kind": "session",
  "body": "{\"protocol\":\"acp-mailbox/1\",\"channel_id\":\"fresh-generation\",\"sequence\":1,\"type\":\"rpc\",\"message\":{\"jsonrpc\":\"2.0\",\"id\":0,\"method\":\"initialize\",\"params\":{\"protocolVersion\":1,\"clientCapabilities\":{}}}}"
}

The string body contains a structured object. Its payload is either {type:"rpc", message:<JSON-RPC object>} or {type:"closed", reason:<string>}. RPC IDs retain their JSON type; numeric zero is valid. Numbers must be safe integers (absolute value at most 2^53 - 1). Arbitrary ACP content blocks, tool inputs, results and extension metadata are preserved. The maximum encoded envelope is 4 MiB.

Each direction starts sequence at 1. A receiver ignores its own writes, other generations and sequences already consumed. A sequence gap, wrong participant, malformed message or unknown protocol closes the channel. Reading can start at offset zero because generation and sequence checks suppress historical frames. The codec and cursor remain alive across transient read failures. A new codec cannot attach to an already-used generation and start sending from sequence 1.

Turns, approvals, questions and cancellation

OperationMessage and behavior
Start turnController requests session/prompt with the durable sessionId and content blocks. One session serializes turns.
Stream outputAgent emits session/update for text, reasoning, tool_call and tool_call_update, including failed tools. Updates are drained before the terminal prompt response.
Approve a toolAgent issues session/request_permission with its own request ID, toolCall and advertised options. Controller replies to that ID with outcome selected plus optionId, or outcome cancelled. A missing or failed approver denies execution.
Ask a questionAgent issues _scode/ask_user_question; controller replies to the same ID with answers [{id,value,label}]. This does not grant tool permission.
Cancel turnController sends session/cancel as a notification. It bypasses the turn lane and wakes pending permission/question waits. The pending prompt ends with stopReason cancelled. The next turn remains usable.
Close attachmentA closed frame ends this run; the host cancels pending work and releases its writer lease. managed_agent.cancel_v1 with mode session also terminates the run. Its old mode turn now returns an error directing callers to session/cancel.
DiagnosticsThe subprocess adapter carries stderr as _nexus/diagnostic notifications with {stream:"stderr",text}. It uses the same channel.

The reader runs independently of the turn worker and of UI approval callbacks. A pending approval must not prevent receiving its answer or cancellation. Co-host reports busy/awaiting_input/ready through the existing agent state stream. Prompt mode explicitly consults the approver for each tool level unless an explicit policy allow rule applies.

For example, while prompt request "turn-1" is pending, the agent may request permission with ID 0. The controller replies with {jsonrpc:"2.0",id:0,result:{outcome:{outcome:"selected",optionId:"allow-once"}}}. This is the answer to the reverse request, not the answer to "turn-1". Cancellation clears pending UI approval IDs. A late response from a previous generation is ignored before reaching the engine.

Ordinary A2A messages

Scode normalizes peer text to a prompt in the same turn driver used by session/prompt. It marks the sender and neutralizes privileged prompt markup. The bound controller receives updates, tool approval requests and questions. The sending peer supplies input; it does not acquire authority to approve tools. kind=session is reserved for structured traffic and never becomes model text.

The peer conversation's durable read position advances after the turn finishes. A prose response is delivered once as kind=auto_reply unless the turn already called send. An auto_reply does not generate another automatic reply. This text compatibility uses the existing conversation receiver and shared turn driver; there is no second ConversationRuntime loop.

Failure and recovery

  • Transient read failures retry at the same record cursor with bounded backoff. They do not replay UI events.
  • An append failure has an unknown delivery outcome. The transport closes and does not silently resubmit a prompt. Identical encoded frames can be deduplicated within a live generation, but allocating a new sequence is a new message.
  • A host restart requires a fresh start call and channel generation. Resume the durable session ID, then load it through ACP. Old prompts and approval replies cannot drive that new run.
  • Only a terminal prompt response establishes the observed turn outcome. A connection loss before it may leave persisted tool effects or a partial transcript. Recovery must inspect that transcript; this protocol does not promise exactly-once tool execution across crashes.
  • Co-host holds one writer lease per durable session and rejects concurrent starts or a changed agent/owner/zone/repository identity. Close releases the lease after stopping the turn.

Implementation and rollout

The wire codec, authenticated kernel transport and subprocess adapter live in nexus-vfs. Sudocode engine-acp hosts the shared ACP handlers and peer normalization; engine-host supplies SessionEngine and direct Kernel-backed storage. nexusd-cohost composes these with its websocket feature disabled. The kernel never depends on sudocode.

Release order

Removing the fd interface is a breaking daemon change: target the next minor daemon release, v0.8.0, and Node SDK 0.5.0. These are proposed release versions, not published artifacts. A release tag must identify the reviewed source; retain cloud co-host as disabled throughout preparation.

  1. Review and merge nexus-vfs, then publish the daemon and SDK. Verify the actual release artifacts and checksums before changing consumer locks.
  2. Update all eight Nexus dependency tags in sudocode together, regenerate Cargo.lock from the published source, and run the locked driver-ai co-host build and authenticated mailbox end-to-end test. Its CI deliberately requires a published daemon tag; do not replace that guarantee with a branch dependency.
  3. Update Moss and Sudowork to the published SDK URL and regenerate their Bun locks. In Sudowork also update both nexus-vfs and nexusd-cluster in runtime-versions.json and every matching daemon checksum in runtime-sha256.json. Preserve the independently versioned plugin checksums.
  4. Run clean installs, consumer tests, and the real SDK smoke against the pinned daemon. Publish the matching co-host and consumer artifacts, then deploy the compatible set. Upgrading only the daemon breaks old fd clients.

Release nexus-vfs and Node SDK 0.5.0 first; pin every Nexus workspace crate in sudocode to the same revision; then build nexusd-cohost and update moss and sudowork together. Keep cloud co-host disabled until that compatible set is deployed. Remove fd clients and the Kubernetes direct-spawn bypass in the client update. Protocol mismatch is a visible setup failure.
