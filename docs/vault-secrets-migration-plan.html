SecretStoreClient → Vault Plugin 迁移方案

nexus#4326 · 2026-06-08 · Architecture Decision: Option A (扩展 vault plugin)

1. 背景与动机

sudowork 的 SecretStoreClient 当前通过 HTTP /api/v2/secrets 调用 Python SecretsService，用于管理 AI 平台 API keys、channel credentials、JWT secrets 等敏感数据。

nexus#4326 已将 vault 从 standalone binary 转为 cdylib plugin，通过 declare_service_plugin! 宏注册到 kernel 的 ServiceRegistry，由 nexusd-cluster --plugin-dir 加载。

目标：将 sudowork 的 secrets 调用切到 gRPC plugin dispatch，消灭对 Python SecretsService 的依赖。

关于 Auto-login / Auto-rotate：这两个功能的逻辑在 password-agent 侧（browser automation + pwd_rotate 脚本），vault plugin 只提供 get_entry / put_entry 数据接口。迁移不影响它们 —— password-agent 仍然调用 put_entry / get_entry / generate_totp，sudowork 调用 secret_put / secret_get，两条路径互不干扰。

选型：Option A — 扩展 vault plugin 为通用 secrets service

核心判断：vault plugin 底层已经是 kernel syscalls 做的 AES-256-GCM encrypted KV 存储。PasswordVaultService 只是在上面加了 VaultEntry schema + TOTP。在 dispatch 中加 secret_put, secret_get, secret_list 等通用方法，password-specific 的 put_entry 等保持不变。一个 plugin，两个 service。

优点

  • 一个 plugin 服务所有 secrets 需求
  • 共享 master key、kernel mount、加密基础设施
  • 零重复代码（StoredEntry, crypto::seal/open 复用）
  • 两个 service 的 VFS 路径互不冲突

注意事项

  • vault plugin scope 扩大（需要 architecture sign-off）
  • Enable/Disable 功能暂不迁移（coupled to tenant config，sudowork 侧逻辑）
  • deleteVersion 和 updateDescription 暂不迁移（低频，可后续加）

11.5 回滚方案

如果迁移后出现问题：

# 1. 回退 sudowork 到旧版（HTTP backend）
pm2 stop sudowork
# 部署旧版代码
pm2 start sudowork
# sudowork 会重新连接 Python SecretsService（PostgreSQL 备份数据仍在）

# 2. nexusd-cluster 不需要回退（vault plugin 向后兼容，不影响其他功能）
# 如果需要，可以不加载 plugin：去掉 --plugin-dir 参数即可

# 3. 验证回滚成功
pm2 logs sudowork --lines 20 | grep "SecretCache.*preload"
# 期望: "preloaded N secrets from HTTP backend"

数据安全保障：

  • SQLite 原始数据始终只读保留（coordinator 标记 isMigrated 但不删除原始值）
  • PostgreSQL 备份在 Step 0 已保存
  • vault plugin 的 AES-256-GCM 数据是新写入，回滚时不影响旧数据
